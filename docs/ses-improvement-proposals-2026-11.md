## 2. 見つかった問題

### P1. 本番バッチは「メール収集に失敗」しても営業リストを書き換える【ログ】【コード】

- 失敗の原因は、メールサーバーへの接続失敗（`NoConnection`）です。11/4 夜から毎回起きています。
- `src/ses/index.ts` は収集の失敗を `recordFatal` に記録するだけで、処理を続けます（548〜557 行付近）。
- その結果、新着 0 通のまま「直近 14 日の案件」だけで判定し直し、営業リストを書き出していました（11/9 の回は「4 行を書き出しました」）。
- このとき、試運転が足した未着手の行は「今回の候補にない行」として期限切れへ移されました（11/9 に 11 行、11/10 に 12 行）。

### P2. 担当の引き継ぎ（`handoff.ts`）が、止めたい本番を止められない【ログ】【コード】

- 本番は起動するたびに API 残高を確かめ、残高があれば担当を `api` に書き戻します。人が `trial` にしても戻ります。
- 「人が止めた」状態を表す値がありません。
- 本番と試運転が同じ「全体」タブを書くのに、書く直前に担当を確かめる仕組みがありません。

### P3. 定時実行が時刻どおりに動いていない【ログ】

- cron は UTC 0・3・6・9 時（平日）ですが、実際に動いたのは 1 日 2 回ほどで、時刻も 2〜5 時間ずれていました（例: UTC 4:55・13:50・15:23）。
- 無料枠の GitHub Actions の定時実行は、混雑時に遅れたり飛んだりします。営業が見る時刻に合わせる用途には向きません。

### P4. 営業に届く候補の質が低い【ラベル】【運用】

- 載せた約 900 行のうち、提案まで進んだのは 1 行です。
- 見送り理由で最も多いのは「ハードルが高い（スキル・経験不足）」（79 件）です。
- 載る行のほとんどが B で、B の典型は次の 3 つです。
  1. 必須の経験年数に少し足りない（例: 3 年以上に対し 2.8 年）
  2. 案件単価が希望より 15〜25 万円高い（求める水準が高い見込みと自分で書いている）
  3. 必須の工程（基本設計など）が未経験
- 2 と 3 が重なる行（高単価かつ必須が△）は、営業の見送りとよく一致します。

### P5. 営業が理由に書いた軸を、足切りが見ていない【コード】【運用】

営業のメモに出た理由は次の 3 つで、どれも今の足切りを通ります。

| 営業のメモ | 今のコード |
|---|---|
| 開始時期が合わない／希望の開始月に間に合わない | `isTimingWithinGrace`（`match.ts` 657 行）は「要員の稼働開始が案件の開始より遅すぎないか」だけを見る。案件の開始が要員の稼働開始より**ずっと後**（待機が出る）場合は通る |
| 通勤距離が遠すぎる | `ownMatch.ts` は「同じ地方か」だけを見て、通勤時間は見ない（161 行のコメントどおり）。神奈川の要員に千葉の東側の常駐案件が載った |
| 夜勤 NG（要員の希望に追記された） | 希望欄は判定の文面に渡るが、足切りの条件ではない |

### P6. 営業のメモがラベルに残らない【コード】

- ラベルストアの営業側の行は `status`・`skipReason`・`check`・`checkMemo` を持ちますが、「メモ」列を持ちません。
- 見送り理由の「その他」（66 件）の中身はメモに書かれていることが多く、いちばん役に立つ情報を捨てています。

### P7. 同じ案件が要員ごとに何行も並ぶ【運用】

- 研修明けの要員 3 人に、同じ未経験可の案件が 1 行ずつ載りました（計 3 行）。
- Java の要員 2 人にも同じ案件が 2 行載ることがよくあります。
- 営業は同じメールを要員の数だけ読むことになります。

### P8. 営業リストの行が短い時間で入れ替わる【運用】

- 「全体」の行数は 1 日のうちに 28 → 6 → 14 → 16 → 6 と動きました。
- 原因は P1（本番による期限切れ）のほか、試運転自身も「今回の候補にない未着手の行」を期限切れへ移すためです。
- 営業が朝に見た行が昼には無い、ということが起きます。

### P9. 試運転の運用が重く、手作業が多い【運用】

- 1 回に 2.6M〜5.4M トークンを使います。内訳は一覧 0.4M（ページ送りに変えた後）・抽出 0.5〜2.1M・判定 0.6〜1.9M・書き込み 0.1〜0.2M・ラベル控え 0.1M です。
- スプレッドシートの読み取りが大きすぎます。
  - 「全体」を `includeGridData` で読むと、10 行でも 1MB を超えます（書式が全部入るため）。
  - 「ラベル控え」は毎回 2 回、全行（いま約 11,000 行・1.8MB）を読みます。行が増えるほど重くなり、11/6 には 1 万行の上限にも当たりました。
- 書き込みは、サブエージェントが JSON を見て MCP の引数に貼ります。写し間違いが 1 回に 0〜4 セル出ていました（\u エスケープを貼らせる方法に変えてからは 0〜1）。
- 11/6 には書き込みが途中で止まり、ID の無い半端な行（No.915）が残りました。ID が無い行は、クローズ済みへの移動も照合もできません。
- 手順（`docs/ses-trial-runbook.md` 285 行）は、回ごとに 15 個ほどのコマンドを順に打つ形です。前の回のファイルを写す操作も多く、要員リストの更新や期限切れの ID の扱いを人（AI）が覚えていないと抜けます。

### P10. テストに時間に左右されるものがある【運用】

- `rulesEval.ts` の「ワーカーで解析でき、時間切れなら…」（3156 行付近）が、環境によって落ちます。11/10 は 3 回続けて落ちました。
- 「4 つのチェックが通ったらプッシュ」という決まりが、このテストのせいで判断しにくくなっています。

### P11. 文書とコードのずれ【コード】

- `CLAUDE.md` の「Git ワークフロー」は「main に直接プッシュ」と書いていますが、実際は機能ブランチ＋PR です。
- `CLAUDE.md` のコマンド一覧に `ses:*` がありません。
- 手順書は、ページ送りでの一覧・\u エスケープでの書き込み・要員リストの更新時の読み直しを反映していません（作業用のメモにだけあります）。
- ワークフローが使う Actions は Node.js 20 向けで、実行時に警告が出ています。

### P12. 測定値が不安定で、目標が無い【運用】

- 「判定の引用が本文の写しに無い」割合は、回によって 11.8%〜36.3% と動きます。
- 単価の空き 11〜12%、勤務地の空き 6〜7% は横ばいです。
- 点数は付けておらず、どの値がいくつなら良いのかが決まっていません。

#### C1. 試運転を 1 本のコマンドにまとめる

- **ねらい**: P9。手順の抜けと、前の回のファイルを写す操作をなくします。
- **変える場所**: `src/ses/trial/` に入口を 1 つ足す（例 `ses:trial:run <段階>`）。`harness.ts` の各 `PHASE` を呼ぶ薄い層です。
- **やり方**:
  - 回の状態（前回の終わり・使った No.・クローズ済みと期限切れの ID）を、回ごとのフォルダではなく 1 つの状態ファイルに持ちます。

  - MCP で読んだ結果のファイルを渡すと、中身の形（グリッド／values）を見分けて取り込みます。
- **終わりの条件**: 手順書の「回ごとのコマンド」が 5 行ほどになり、前の回のフォルダを指定しなくても動く。
- **規模**: L
- **決めること**: 状態ファイルの置き場所（スクラッチパッドは消えることがある。控えを表計算に置くか）。

#### C2. スプレッドシートの読み取りを小さくする

- **終わりの条件**: ラベル控えの読み取りが 1 回あたり数 KB になる。照合が合わないときだけ全行を読む。
- **規模**: M

#### C3. 書き込みを安全にする

**通勤の表の注意（B3）**

- 県をまたぐだけでは外しません。埼玉→東京、神奈川→東京、千葉→東京は普通の通勤です。
- 外すのは「東京をはさんで反対側」や「県の端から端」のように、明らかに遠い組だけにします。例: 神奈川↔千葉の東側、埼玉↔神奈川の西側、群馬↔神奈川。
- そのため、表は「都道府県 × 都道府県」ではなく、要員の最寄り駅の地域と、勤務地の地域で引けるようにします。東京・神奈川・千葉・埼玉は、県を 2〜4 つの地域に分けておきます（例: 神奈川は横浜・川崎／湘南・県央／県西）。
- 勤務地が駅名しか分からないときに地域を決められない場合は、外さずに通します（今の「不明なら通す」と同じ）。
- 要員のサマリに「通勤 150 分程度問題ありません」のような記載があれば、その要員には表を当てません。
- 入れる前に、ラベルストアの過去の組に当てはめます。営業が「提案済」にした組と、「勤務地・通勤」以外の理由で見送った組が、どれだけ外れるかを数えて報告します。
